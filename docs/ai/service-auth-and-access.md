# 작업 09 — 서비스 인증과 JEV 접근 인가

상태: 09번 완료 — JEV 경로 구현과 자동 검증 완료. 실제 환경변수·키 입력과 운영 배포는 수행하지 않았다.
인증은 두 구간으로 분리하고 서로 다른 자격증명을 사용한다.

```text
사용자 앱 ── 로그인 JWT ──> Spring /ai/jev, /ai/jev/{analysisId}
                           서명·발급자·시간·계정 상태·역할 검증
                           청구 참여자 및 파일 소속 확인
                           접근 감사 DB 기록
                              │
                              └─ 서버 전용 Bearer 토큰 ──> FastAPI /internal/jev
                                                         본문 읽기 전에 인증
                                                         PDF 검증·모델 실행
```

## 사용자 인증과 역할

Spring JEV API의 Authorization에는 기존 로그인 API에서 받은 accessToken을 넣는다.
X-User-Id·X-User-Roles는 JEV의 행위자 식별이나 권한에 사용하지 않는다.
기존 헤더를 함께 보내더라도 JWT로 검증한 계정만 사용한다.
Spring의 JEV 요청 ID 필터 다음에 인증 필터를 실행해 인증 실패에도 X-Request-ID를 제공한다.

검증 항목:

- RS256만 허용하고 현재 공개키로 서명을 확인한다.
- iss는 기존 발급기의 insai-auth와 일치해야 한다.
- exp는 현재보다 미래여야 하며 만료 시각과 정확히 같은 순간도 거부한다.
- iat는 필수이고 미래일 수 없으며 exp보다 앞서야 한다. nbf가 있으면 현재 이후일 수 없다.
- sub는 표준 UUID, roles는 기존 단일 역할 형식의 알려진 역할이어야 한다.
- DB에 계정이 있고 ACTIVE 상태여야 하며 현재 역할과 토큰의 역할이 일치해야 한다.
- JEV는 CLAIMANT·ADJUSTER만 허용한다. ADMIN에 의료 문서 접근 우회 권한을 부여하지 않는다.
- Authorization은 한 개만 허용한다. 잘못된 형식·중복·과대 헤더를 거부한다.

계정 정지·삭제·역할 변경은 다음 요청의 현재 계정 검사에 반영한다.
로그아웃에 따른 개별 accessToken 즉시 폐기나 실행 중 작업 취소까지 구현한 것은 아니다.
잘못된 JWT에는 원문·파서 예외를 노출하지 않고 401을 반환한다.
역할상 JEV가 허용되지 않으면 403, 인증 저장소 장애는 안전한 서비스 실패로 처리한다.

## 청구 건과 문서 인가

| 요청 | 허용 조건 |
|---|---|
| 분석 요청 | ACTIVE 청구인 또는 사정사이고 해당 청구 건의 청구인/배정 사정사임 |
| PDF 읽기 | 요청 청구 건의 참여자이며 저장된 파일의 caseId가 요청과 같음 |
| 결과 조회 | 저장된 분석의 caseId를 기준으로 참여자를 다시 검사함 |

같은 계정 소유라도 다른 청구 건의 파일을 섞을 수 없다.
사정사 역할만 있다고 다른 사정사 배정 건을 볼 수 없다.
거부 시 파일 스토리지 읽기·모델 호출·성공 결과 저장으로 진행하지 않는다.
파일 ID를 업로드한 사용자라는 사실만으로 다른 케이스의 분석 권한을 주지 않는다.

## 내부 서비스 인증

FastAPI의 보호 대상 POST /internal/jev는 JEV_SERVICE_TOKEN과 상수 시간 비교를 사용한다.
현재 하나의 서버 전용 토큰을 spring-insai 서비스 주체에 대응시킨다.
사용자 JWT·Gemini 키·쿼리 문자열의 access_token·스푸핑된 사용자 헤더는 대체 인증 수단이 아니다.
서비스 토큰과 공급자 키를 같은 값으로 설정하면 시작 설정 검증에서 거부한다.
중복 Authorization을 거부하고, 인증을 통과하기 전에 본문·PDF를 읽거나 공급자를 초기화하지 않는다.
마지막 슬래시가 있는 URL도 인증을 우회해 리다이렉트되지 않도록 검사한다.
OpenAPI Bearer 인증 스키마와 라우트 의존성 검증도 유지한다.

토큰 미설정은 503, 누락·불일치·잘못된 종류는 401이다.
health/live·health/ready·version은 비밀값을 반환하지 않는 공개 운영 조회로 유지한다.
Spring의 HTTP 어댑터는 사용자 Authorization을 전달하지 않고 서버 설정의 토큰으로 새 헤더를 만든다.
내부 인증 실패를 공개 사용자 로그인 실패로 오인하지 않도록 08번의 503 변환을 유지한다.

서비스 토큰은 소유를 증명하는 공유 비밀이며 Spring 프로세스 자체를 원격 증명하거나
인증된 사용자의 케이스 접근 권한을 FastAPI에서 독립적으로 재검사하는 방식은 아니다.
FastAPI에는 업무 DB 자격증명·쓰기 권한을 주지 않는다.

## 사용자·역할·케이스 전달 규칙

- 검증한 사용자 ID와 역할은 Spring 안의 Actor로 전달한다. 클라이언트 헤더를 Actor로 복사하지 않는다.
- caseId는 Spring의 권한·파일 소속 검사와 영구 결과 연결에 사용한다.
- FastAPI에는 필요한 request_id, 문서 ID·종류·PDF만 보낸다.
- 사용자 ID·역할·caseId는 Gemini 프롬프트나 LangSmith 메타데이터로 보내지 않는다.
- Spring의 감사 기록과 분석 결과를 request_id로 연결해 호출 주체와 결과를 추적한다.

## 접근 감사

V7 마이그레이션으로 Spring의 jev_access_audits 테이블을 추가했다.
요청 ID, 검증된 행위자 ID, 대상 케이스/분석 ID, ANALYZE/READ, ALLOWED/DENIED,
고정 사유 코드, 시각을 기록한다. 토큰·PDF·문서명·판정 원문·예외 메시지는 저장하지 않는다.
업무 데이터처럼 식별자를 포함하는 제한된 감사 저장소이며 일반 로그나 LangSmith가 아니다.
행위자 인증에 실패한 토큰에서 sub를 임의로 추출해 '검증된 사용자'로 기록하지 않는다.

허용 분석은 파일 검증 후 모델 호출 전에 감사 저장을 완료한다.
감사 저장에 실패하면 모델 호출이나 결과 반환을 진행하지 않는다.
거부 기록은 REQUIRES_NEW 트랜잭션으로 남겨 업무 오류 반환 후에도 조회할 수 있다.
ALLOWED는 접근 허용이라는 뜻이며 모델 처리 성공이나 사정사 승인이라는 뜻은 아니다.
승인·수정·거절 이력, 감사 기록 조회 API·보존/삭제 정책은 27번에서 다룬다.

## 범위와 운영 한계

이번 변경은 /ai/jev 및 하위 경로의 사용자 인증과 /internal/jev의 서비스 인증이다.
다른 기존 업무·파일 API는 여전히 별도 통합 인증 보강이 필요하며 전체 서비스의 외부 공개 준비 완료가 아니다.
기존 JWT 키는 부팅 시 생성돼 재시작하면 이전 토큰이 무효화된다. 영구 키 관리·회전은 아직 미구현이다.
공유 토큰의 무중단 회전, 서비스별 토큰·scope 확장, mTLS·배포 네트워크 정책은 아직 없다.
운영에서는 FastAPI를 내부 네트워크에 두고 서비스 구간 TLS 및 비밀정보 주입을 적용해야 한다.
이번 작업에서 사용자 계정·외부 네트워크 정책·실제 키를 변경하지 않았다.
V7은 다음 Spring 실제 DB 시작 시 적용되며 이번에는 테스트 H2에서 엔티티 저장을 검증했다.

## 검증

2026-10-20 중단 후 재검증 결과:

- Spring 전체 테스트 275개 통과, 실패·오류 0건.
- Python 3.11 및 3.14에서 각각 85개 테스트 통과.
- 두 Python 환경에서 Ruff 검사·포맷 검사와 mypy 통과.
- 임시 로컬 포트의 HTTP 스모크 테스트 통과: 운영 엔드포인트, 요청 ID, 본문 검증 전 서비스 인증.
- 실제 PostgreSQL의 V7 적용, 운영 배포 및 실제 Gemini 호출은 이번 검증 범위가 아니다.

실제 테스트용 RSA JWT와 H2 계정·케이스·파일 메타데이터로 다음을 확인한다.

- 정상 JWT의 주체 사용, X-User-Id 스푸핑 무시, 헤더만 있는 요청 거부.
- 만료·변조·잘못된 발급자/알고리즘/시간·잘못된 sub 거부.
- 정지·대기 계정 거부, ADMIN 우회 금지, 현재 역할 불일치 거부.
- 타 케이스 파일, 비참여자 분석·결과 조회 거부, 배정 사정사 조회 허용.
- 실제 허용·거부 감사 기록 저장, 감사 실패 시 모델 미호출.
- FastAPI의 중복/잘못된 인증·사용자 JWT·쿼리 토큰 거부와 본문 읽기 전 인증.

검증에는 가짜 모델과 파일 스토리지를 사용한다. 실제 공급자나 환자 문서를 사용하지 않는다.
인증 설계 참고: [Spring JWT 검증](https://docs.spring.io/spring-security/reference/6.5/servlet/oauth2/resource-server/jwt.html),
[FastAPI 보안 도구](https://fastapi.tiangolo.com/reference/security/).
이 구현은 기존 Nimbus 발급·검증 포트를 이용하는 JEV 필터이며 Spring OAuth2 Resource Server를 새로 활성화한 것은 아니다.
