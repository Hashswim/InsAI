# 작업 24 — 안전장치·입력 방어

이번 범위는 FastAPI JEV 입력과 표준 운영 로그의 방어 보강이다.
보안 인증·악성코드 검사·의미적 프롬프트 주입 방어 완료를 뜻하지 않는다.
프론트·실제 키·환경변수·의료 제출 규정은 변경하지 않았다.

## HTTP·JSON 경계

- POST /internal/jev 및 trailing-slash 경로는 기존 서비스 인증·요청 한도를 본문 읽기 전에 검사한다.
  인증 실패 시 본문·PDF를 파싱하거나 모델을 호출하지 않는다.
  ASGI root_path 마운트 접두사가 있어도 라우터와 같은 경로 기준으로 이 검사를 적용한다.
- X-Request-ID는 헤더 하나, UUID 표현 36자만 허용한다. 중복/비정상 값은 400이며 값을 되돌려 쓰지 않는다.
- JEV는 Content-Type 헤더 하나의 application/json만 허용한다. 선택적 charset=utf-8/utf8 하나만 지원한다.
  Content-Encoding은 없거나 identity여야 한다. 압축 본문은 풀지 않고 415로 거절한다.
- 중복 Content-Length/Transfer-Encoding, 두 헤더의 동시 사용, 지원하지 않는 transfer coding은 422다.
  chunked는 Content-Length가 없을 때 허용한다. 선언된 길이와 실제 수신 길이가 달라도 422다.
- 기존 JEV 본문 상한 43,000,000바이트를 선언 길이·스트림에 모두 적용한다.
  나머지 경로의 본문은 64KiB로 제한한다. 초과는 413이다.
- JEV JSON은 UTF-8 객체 하나, 중첩 최대 32단계다. 모든 깊이의 중복 키,
  이스케이프로 같은 이름이 된 키, NaN/Infinity/수치 overflow, 잘린/이어 붙인 JSON,
  잘못된 UTF-8·UTF-16 JSON을 422로 거절한다.
- JSON 수신 방어와 모델 출력 파서는 공통 json_guard를 사용한다. 모델 출력의 기존 1MiB/4MiB 상한은 유지한다.
- 헤더/본문 request_id 불일치는 PDF 파싱과 모델 SDK 구성 전에 422로 거절한다.
  일반 PDF/스키마 오류에서는 SDK 객체 구성이 선행될 수 있지만 유료 모델 분석은 실행하지 않는다.
- 모든 응답(성공·오류·health 포함)에 no-store와 nosniff를 설정한다.
  오류 응답은 기존 고정 코드·메시지·요청 ID만 사용하며 JSON/PDF 원문을 노출하지 않는다.

HTTP 서버나 앞단 프록시가 먼저 거절하는 잘못된 wire framing은 앱의 오류 봉투로 보장할 수 없다.
프록시의 요청 크기·시간·헤더 제한과 서버 간 TLS/네트워크 격리는 별도 운영 설정이 필요하다.

## PDF 수용 정책

기존 파일당 10MiB·30페이지·비암호화·유효한 PDF 조건에 아래 기술적 제한을 추가했다.
이는 **분석 서비스의 입력 조건**이며 법적 제출 규정이 아니다.
원본 파일을 자동 수정·평탄화하거나 서명 유효성을 판단하지 않는다.

- 문서 Names의 JavaScript/EmbeddedFiles, 포트폴리오 Collection, 연관 첨부 AF, XFA를 거절한다.
- 문서 OpenAction/추가 액션, 페이지·주석·폼 필드의 A/AA, 후속 Next 액션을 검사한다.
  GoTo와 URI 이외의 액션(예: JavaScript·Launch·SubmitForm·GoToR 등)은 거절한다.
- URI는 http/https/mailto/tel만 지원한다. URI를 방문하거나 다운로드하지 않는다.
- RichMedia·3D·Movie·Sound·Screen·FileAttachment 등 선언된 주석 기능을 거절한다.
- 일반 문서, 활성 기능 없는 폼, 초기 보기 목적지와 지원하는 정적 링크는 허용한다.
  형식이 지원 범위 밖이면 일부 정상 대화형 PDF도 거절될 수 있다.
- 액션 그래프는 256개, 탐색 구조는 1,000개, 페이지당 주석은 200개 상한이다.
  같은 객체의 순환 참조는 방문 집합으로 처리한다. 이 상한은 선택한 구조 탐색의 한도이지
  PDF 전체 객체 수나 파서 메모리 상한이 아니다.

공식 [pypdf Writer 문서](https://pypdf.readthedocs.io/en/6.9.2/modules/PdfWriter.html)는
JavaScript와 파일 첨부 기능을 설명한다. 해당 API와 합성 PDF 구조로 차단/허용 테스트를 구성했다.
기능 검출은 선택된 표준 구조를 읽는 보수적 검사이며 모든 PDF 확장·난독화·취약점을 탐지하지 않는다.
Spring의 원본 업로드 저장소 전체를 검사하는 바이러스 검사기로도 동작하지 않는다.

거절된 PDF는 고정된 INVALID_INPUT이다. 진단 로그에 원문·첨부 이름·스크립트 등을 남기지 않는다.
지원되지 않는 문서는 원본을 보존한 채 지원 가능한 PDF를 별도로 준비해야 한다.

## 모델·로그 경계

기존 도구 미제공, 고정 공급자 URL, PDF를 비신뢰 입력으로 취급하는 프롬프트,
엄격한 Findings 스키마·J/E/V 검사, ON_HOLD·사람 검토 필요 정책을 유지한다.
모델이 요청한 명령·URL·파일 접근을 실행하는 기능은 추가하지 않았다.
문서 속 지시문을 정규식으로 탐지해 완벽히 차단했다고 주장하지 않는다.
스키마에 맞는 잘못된 판정·의료적 환각·모든 식별정보의 반복을 자동 탐지하는 것도 아니다.

표준 logging factory에서 다음 라이브러리의 메시지/예외/스택을 고정 진단 메시지로 바꾼다:
google.genai, langchain_google_genai, langchain_core, langsmith, pypdf, httpx, httpcore, uvicorn.access.
로그 수준·로거 이름은 유지한다. 그 외 표준 로그의 설정된 키 마스킹은 기존대로 유지한다.
원문 없는 수동 LangSmith 허용 목록, 빈 inputs/outputs, 자동 tracing 비활성화도 유지한다.

이 필터가 print, Python warning 출력, 외부 프록시, 사용자 정의 extra/직접 파일 기록까지
모두 정화하지는 않는다. 일반 업무 로그에 의료정보를 기록하지 않는 코드 정책도 계속 필요하다.
Makefile/Docker의 --no-access-log도 유지한다. 모델 결과는 민감한 업무 데이터로 저장하며,
프론트는 신뢰할 수 없는 일반 텍스트로 렌더링해야 한다. 이번에는 프론트 수정·XSS 검증을 하지 않았다.

## 검증·남은 운영 조건

중복 키/헤더·인코딩·중첩·본문 길이·인증 전 미수신·ID 불일치의 조기 거절,
잘못된 요청 이후 동시성 슬롯 해제, 정상 UTF-8/chunked 계약,
활성 PDF·암호화·후속 액션 차단, 정적 링크/폼 허용, 탐색 상한/순환 종료,
로그·응답의 합성 민감 문자열 비노출을 자동 검사한다.
실제 사용자 PDF·키·실제 모델·LangSmith 계정으로 공격 평가를 수행한 것은 아니다.

PDF 파싱은 현재 프로세스 안에서 실행한다. 압축 폭탄·거대한 페이지 트리·라이브러리 취약점에 대한
CPU/메모리 hard limit·시간 제한·독립 worker sandbox·악성코드 스캔은 미구현이다.
실서비스에 실제 의료 파일을 투입하기 전에 격리된 파일 처리, 공급자 데이터 처리 조건,
TLS·네트워크·분산 한도·보존/삭제·실모델 공격 평가를 별도로 검증해야 한다.

체인은 jev-chain-v7이다. 프롬프트 jev-v2와 해시, 응답 필드, 업무 DB 구조는 변경하지 않았다.
규정 파일은 빈 상태이며 최종 제출 여부는 여전히 ON_HOLD다.
