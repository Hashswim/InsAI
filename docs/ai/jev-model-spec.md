# 작업 01 — JEV 결정 모델 명세

상태: 명세 완료. 적용 범위: 의료 청구 서류 작성 상태에 대한 판단 추천.
이 문서는 목표 동작을 정의한다. 코드 반영과 실모델 검증 여부는 별도로 표시한다.
API 필드와 호출 방법은 [API 계약](jev-contract.md)을 따른다.

## 목적과 입력

진단서, 진료확인서, 병원비 세부내역서 각 PDF 한 개를 받아 항목의 작성 상태를 확인한다.
입력에는 케이스 ID, 문서 ID, 사용자가 지정한 문서 종류와 PDF가 포함된다.
같은 청구 건의 파일만 사용한다. 사용자가 지정한 종류와 실제 문서가 다른지도 확인한다.
규정 파일은 비워 둔다. 현재 관찰 항목은 서비스 점검 항목이며 법적 필수 항목 목록이 아니다.

## J — Judgment: 항목 판정

입력: PDF의 판독 가능한 내용과 문서 종류.
처리: 항목의 기재 상태, 해석 가능한 형식, 같은 의미를 가진 정보의 문서 간 일치 여부를 확인한다.
출력: 항목명과 잠정 판정. 원문에 없는 정보는 만들어 채우지 않는다.

| 판정 | 적용 조건 |
|---|---|
| SUITABLE / 적합 | 점검한 범위에서 작성 상태를 확인했고 모순을 찾지 못함 |
| NEEDS_SUPPLEMENT / 보완 필요 | 판독 가능한 근거로 빈 항목, 명백한 형식 오류, 불일치 등을 확인함 |
| UNVERIFIABLE / 확인 불가 | 흐림, 잘림, 모호함, 비교 대상 부족 등으로 판단 근거가 부족함 |

관찰할 항목: 문서 종류, 환자 정보의 일치, 발급기관 기재, 날짜의 해석 가능성,
같은 사건·같은 의미의 날짜 일치, 진단 내용, 진료 내용, 명시된 비용 항목·수량·합계.
관찰하지 못한 항목을 검사했다고 표현하지 않는다.
발급일과 진료일처럼 의미가 다른 날짜를 단순히 값이 다르다는 이유로 불일치 처리하지 않는다.
다른 병원 발급이라는 사실만으로 오류라 단정하지 않는다.
본인부담·공단부담·할인 등 계산 기준이 불분명하면 단순 합계 비교를 확정하지 않는다.
존재하지 않는 필드를 규정상 필수라 추정하지 않는다. 인쇄된 항목의 명확한 공란은 작성 상태로 지적할 수 있다.

## E — Evidence: 근거 연결

입력: J의 잠정 판정과 문서 내용.
처리: 각 판정에 실제로 확인한 문서 ID, PDF 페이지(1부터), 최소한의 근거 설명을 연결한다.
출력: evidence 배열. 문서 간 불일치에는 비교한 양쪽 문서의 근거를 연결한다.
공란을 근거로 삼을 때는 해당 양식 항목이 있는 페이지와 공란이라는 관찰을 기록한다.
확인 불가에서는 근거 배열이 비어 있을 수 있다. 그 외 판정에는 최소 한 개의 근거가 필요하다.
주민번호와 환자 이름 등 식별값을 설명에 반복하지 않고 '환자 정보가 일치함'처럼 표현한다.

## V — Verification: 검증 및 신뢰도

입력: 잠정 판정과 연결한 근거.
처리: 판정과 근거의 일치, 판독 가능성, 모순·불확실성을 점검한다.
출력: 최종 항목 판정, confidence, verification_reason, supplement.
confidence는 모델 자기평가 0~1이며 실제 정확도나 지급 승인 확률이 아니다.
UNVERIFIABLE의 confidence는 0으로 정규화한다.
NEEDS_SUPPLEMENT에는 사용자가 취할 구체적 보완 행동을 작성한다.
확신도가 높아도 규정 충족이나 제출 가능으로 승격하지 않는다.

J→E→V는 논리적인 검토 순서다. 현재 구현은 한 번의 Gemini 구조화 호출에서 수행한다.
서버는 스키마, 근거 존재, 문서 ID와 페이지 범위를 검증한다.
독립 모델의 재판정이나 근거 문장과 PDF의 사실 일치까지 검증하는 구현은 아직 없다.

## 전이와 실패 처리

| 조건 | 처리 |
|---|---|
| 입력이 유효함 | J→E→V 실행 |
| 문서 수·종류·파일 형식·용량·권한이 부적합함 | 모델 실행 전 요청 거부 |
| 규정이 미등록임 | 항목 결과와 별개로 submission_status=ON_HOLD, regulations_status=NOT_REGISTERED |
| 출력 형식이 잘못됐거나 존재하지 않는 문서·페이지를 인용함 | 분석 실패, 성공 결과로 저장하지 않음 |
| 모델 호출이 실패함 | 분석 실패 응답, 원본 청구·사정 상태 유지 |
| LangSmith 기록만 실패함 | 분석 결과 저장, trace_status=FAILED, trace_id=null |
| 결과 생성·검증 성공 | Spring이 결과·근거·모델·프롬프트 버전·trace ID 저장 |

판정 보류는 유효한 분석 결과이며 시스템 오류와 구분한다.
분석 성공도 보험금 지급 승인이나 최종 제출 승인으로 청구 상태를 변경하지 않는다.
규정을 받은 뒤 제출 가능/불가능 정책을 별도 작업으로 정의한다. 지금은 기준이나 임계값을 추정하지 않는다.

## 출력 예시

아래 ID와 내용은 가상 예시다. 확신도 수치는 동작 설명용이며 테스트의 고정 정답이 아니다.

```json
{
  "submission_status": "ON_HOLD",
  "regulations_status": "NOT_REGISTERED",
  "items": [{
    "item": "동일 진료의 진료일자 일치",
    "judgment": "NEEDS_SUPPLEMENT",
    "evidence": [
      {"document_id": "11111111-1111-4111-8111-111111111111", "page": 1, "description": "진료일자가 비교 문서와 다름"},
      {"document_id": "22222222-2222-4222-8222-222222222222", "page": 1, "description": "동일 진료에 대해 다른 일자가 기재됨"}
    ],
    "confidence": 0.9,
    "verification_reason": "동일 진료의 같은 날짜 항목을 판독했으나 값이 서로 다름",
    "supplement": "발급기관에 동일 진료인지와 진료일자를 확인하고 정정 또는 설명을 보완하세요."
  }]
}
```

모델명, 공급자, 토큰 수, 프롬프트 버전, request_id, trace_id/trace_status는 실행 계층이 채운다.
이 예시는 항목 판단 설명용 부분 응답이며 전체 API 요청·응답 예제가 아니다.

## 가상 청구 예제 5건과 기대 결과

모든 예제는 세 종류의 유효한 PDF를 입력으로 가정한다. 아래 D/T/B는 각각 진단서/진료확인서/세부내역서다.
실제 개인 문서를 사용하지 않으며, 예제의 모든 기대 결과에도 최종 제출 상태는 ON_HOLD다.

| ID | 입력 관찰 사실 | J 판정 | E 근거 | V와 사용자 안내 |
|---|---|---|---|---|
| C01 정상 작성 | D1·T1·B1에서 환자 정보 일치, D1 진단 내용과 T1 진료 내용 판독 가능, T1·B1 같은 진료일, B1 명시 항목 10,000+20,000원과 해당 합계 30,000원 | 관찰한 항목 각각 SUITABLE | 각 항목의 D1/T1/B1 페이지 | 판독·비교 가능한 범위에서 적합. 제출 승인으로 표현하지 않음 |
| C02 날짜 불일치 | T1과 B1에 동일 방문의 진료일자가 각각 2026-09-01, 2026-09-02로 명시됨 | 진료일 일치 NEEDS_SUPPLEMENT | T1과 B1 양쪽 | 발급기관에 동일 방문인지 확인하고 날짜 정정 또는 사유 보완 |
| C03 판독 불가 | D1 진단 내용 영역이 흐려 글자를 확인할 수 없음, T/B는 판독 가능 | 진단 내용 UNVERIFIABLE, 다른 판독 가능한 항목은 별도 판정 | D1의 흐린 영역 설명 또는 근거 없음 | 신뢰도 0, 선명한 진단서 재제출 안내. 진단 내용 누락이라고 단정하지 않음 |
| C04 인쇄 항목 공란 | D1의 인쇄된 진단 내용란이 명확히 공란이며 나머지 영역은 선명함 | 진단 내용 작성 상태 NEEDS_SUPPLEMENT | D1의 공란 항목 | 발급기관에 공란 확인·작성 보완 요청. 법적 필수 항목이라고 주장하지 않음 |
| C05 문서 종류 오지정 | T로 지정한 PDF 1페이지에 영수증 제목·수납 항목만 있고 진료확인서가 아님을 확인함 | 문서 종류 NEEDS_SUPPLEMENT, 확인할 수 없는 진료 내용은 UNVERIFIABLE | 해당 PDF 1페이지 | 진료확인서로 지정한 파일을 확인하고 올바른 문서로 교체 안내 |

추가 공통 검증: 요청에 없는 문서 ID 또는 실제 페이지 수를 넘는 인용은 다섯 예제 모두 분석 실패다.
숫자형 confidence의 특정 값 대신 범위, 확인 불가 시 0, 근거 연결, 판정 사유를 평가한다.

## 자동 처리와 사람의 역할

자동 처리: 입력 검증, 문서 분석, 항목별 추천, 근거 연결, 결과 저장, 원문 없는 운영 추적.
사람의 검토: 보완 필요·확인 불가 항목과 문서 해석, 추후 제공되는 규정 적용 결과, 최종 제출·지급 판단.
이 단계에서는 규정 내용이나 법률 해석을 추가하지 않는다.

## 명세 완료 기준과 현재 근거

- J/E/V 각각의 입력·처리·출력과 전이: 이 문서의 단계 및 전이 절.
- 자동 처리·사람 판단 경계: 위 역할 절.
- 예제 3~5건의 입력부터 결과까지 설명 가능: C01~C05의 판정·근거·검증·안내.
- 규정 미등록 동작과 신뢰도 의미 명시: 전이 및 V 절.

문서 작성은 완료했지만 C01~C05의 실모델 정확도는 아직 검증하지 않았다.
현재 프롬프트가 모든 관찰 항목을 빠짐없이 반환하도록 서버가 강제하지 않으며,
작업 20의 [J 체인](judgment-chain.md)에서 날짜 의미·계산 기준·공란/판독 불가 구분을
프롬프트에 반영하고 중복 범위를 차단했다. 양쪽 근거 연결을 포함한 의미적 정확성은
아직 실모델로 검증하지 않았다. 후속 E/V 작업과 28번 평가에서 보강한다.
