# 작업 04 — AI 유스케이스 우선순위

상태: 우선순위와 MVP 범위 확정.
첫 대상은 의료 청구의 진단서·진료확인서·병원비 세부내역서 PDF 각 한 개다.
목표는 Gemini 기반 JEV 추천 한 건의 입력→분석→저장→재조회→원문 없는 추적을 완성하는 것이다.
규정은 미등록 상태로 유지한다. 프론트 개발은 이번 백엔드 범위에 포함하지 않는다.

## 우선순위

아래 P0/P1/P2는 제품 기능의 우선순위다. 28개 개발 작업의 번호나 실행 순서를 바꾸지 않는다.
서비스 기반·보안·테스트는 P0 기능을 완성하기 위한 공통 작업이다.

| ID | 유스케이스 | 순위·포함 범위 | 선택 이유·선행 조건 |
|---|---|---|---|
| UC01 | PDF 내용 판독 및 항목 구조화 | P0 — JEV 내부 처리 | JEV 판단에 필요한 항목·페이지를 읽어야 함. 별도 OCR 시스템이나 범용 구조화 API까지 만들지는 않음 |
| UC02 | 항목별 작성 상태 및 문서 간 일치 확인 | P0 — 핵심 MVP | 작성 상태를 J/E/V로 판정하고 근거·신뢰도 제공. 규정상 필수 여부는 판단하지 않음 |
| UC03 | 보완사항 및 확인 불가 안내 | P0 — 핵심 MVP | 사용자가 수정할 내용을 알 수 있어야 함. 관찰된 공란·불일치·판독 불가만 다룸 |
| UC04 | 제출물 요약·하이라이트 | P1 — MVP 이후 | 검토 편의 기능. JEV 결과의 필수 조건은 아니며 별도 요약 품질 평가 필요 |
| UC05 | 사정 결과 평문화 | P1 — MVP 이후 | 사정사가 작성한 결과를 쉽게 설명. 원 결론·금액 보존 및 오역 평가 필요 |
| UC06 | 규정 기반 제출요건·누락 서류 점검 및 제출 가능 추천 | P2 — 규정 제공 후 | 보험사·상품·규정 버전과 적용 범위가 있어야 함. 현재는 항상 ON_HOLD |
| UC07 | 약관 근거 검색·인용 및 문의 답변 | P2 — 자료 제공 후 | 신뢰할 수 있는 약관, 문서 버전·검색 범위·인용 검증이 필요 |

UC01~03은 세 번의 독립 모델 호출을 뜻하지 않는다. 현재 한 번의 Gemini 구조화 호출에서 함께 처리한다.
UC03의 '인쇄된 항목의 명확한 공란'과 UC06의 '규정상 필수 서류 누락'을 구분한다.
사용자가 지정한 세 문서 종류의 입력 검증은 제품 입력 계약이며 보험사의 법적 제출 요건이 아니다.

## P0 MVP의 사용자 흐름

1. 기존 업무 API에서 청구 건을 만들고 세 종류의 PDF를 등록한다.
2. 사용자가 케이스 ID와 등록된 파일 ID로 분석을 요청한다.
3. Spring이 접근 권한·파일 소속·입력을 확인하고 FastAPI로 전달한다.
4. Gemini가 항목 작성 상태를 분석하고 FastAPI가 출력·근거 참조를 검증한다.
5. Spring이 항목 판정·근거·신뢰도·보완사항·모델·trace 정보를 저장한다.
6. 사용자가 저장된 결과를 조회하고 보완 필요·확인 불가 항목을 검토한다.
7. 규정 미등록에 따라 최종 제출 상태는 판정 보류로 표시한다.

결과 조회가 성공하면 사용자 연결을 유지하지 않고도 이미 저장된 결과는 다시 볼 수 있다.
실행 중 연결이 끊겼을 때 작업이 반드시 완료되거나 재개된다는 보장은 아직 없다.

## P0 결과와 완료 기준

| 영역 | MVP에서 필요한 결과 | 완료를 입증할 검증 |
|---|---|---|
| 입력·권한 | 같은 케이스의 세 종류 PDF만 분석 | 정상 입력, 중복·타 케이스 파일·잘못된 PDF·권한 없음 검증 |
| 항목 판정 | SUITABLE / NEEDS_SUPPLEMENT / UNVERIFIABLE | JEV 명세 C01~C05의 정상·불일치·판독 불가·공란·종류 오류 평가 |
| 근거 | 문서 ID, 1부터 시작하는 페이지, 최소 설명 | 근거 없는 적합/보완 판정과 존재하지 않는 문서·페이지 거부 |
| 신뢰도·보완 | 0~1 자기평가, 확인 불가 시 0, 구체적 보완 행동 | 범위·판정별 출력 검증. 자기평가를 정확도나 승인 확률로 표시하지 않음 |
| 규정 미등록 | ON_HOLD / NOT_REGISTERED | 모든 항목 적합이어도 제출 승인으로 바뀌지 않는지 확인 |
| 저장·조회 | 항목·근거·모델·프롬프트 버전·trace 정보 보존 | 저장 후 재조회 일치와 비참여자 조회 거부 |
| 관측 | 원문 없는 실행 시간·모델·토큰·성공/실패 | 자동 테스트와 실제 LangSmith trace의 전송 내용 확인 |
| 장애 | 원문 없는 오류, 원 청구 상태 유지 | 공급자 장애·잘못된 출력·LangSmith 장애 시나리오 검증 |

위 기준을 만족하는 '구현'과 실제 계정·PDF로 확인한 '실연결 검증'을 별도로 기록한다.
현재는 자동 테스트 기반 골격이 있으며, 실제 Gemini·LangSmith 연결 및 의료 문서 정확도는 미검증이다.
C01~C05는 문서상 가상 예제이고, 현재 claim_example.json은 실 PDF 평가 데이터셋이 아니다.
실모델 평가는 익명화 또는 합성 PDF와 사람이 확인한 기대 결과로 수행한다.
허용 정확도·지연·비용의 수치 기준은 측정 없이 임의로 완료 처리하지 않고 28번 평가에서 정한다.

## 기존 기능과의 관계

| 기존 경로 | 확인한 상태 | 이번 결정 |
|---|---|---|
| RuleBasedAiStructurePort / LlmAiStructurePort | 양식 제출 시 구조화 포트, 설정에 따라 Java LLM 경로 사용 | 보존. UC01 의료 PDF 분석과 같은 기능으로 간주하지 않음 |
| POST /ai/review-summary | ReviewSummaryService와 Java LlmClient 연결 코드 존재; 컨트롤러는 현재 제출 데이터와 빈 OCR 목록 전달 | UC04는 후속. PDF 요약이나 실모델 검증이 끝났다고 표시하지 않음 |
| RegisterDecisionService / LlmDecisionTranslator | 사정사 결정 등록 시 평문화 연동 코드 존재 | UC05는 후속. JEV가 사정사 결정을 생성하는 경로로 바꾸지 않음 |
| POST /ai/jev, GET /ai/jev/{analysisId} | FastAPI 연결·결과 저장·조회 코드 존재 | P0의 주 경로. 이후 작업에서 검증과 부족한 구현을 보강 |

기존 Java AI 기능을 제거하거나 즉시 FastAPI로 이관하지 않는다.
25번에서 전환할 때 각 기능의 계약과 실패 시 기존 업무가 유지되는 동작을 검토한다.
새로운 의료 PDF 분석을 위해 기존 INSAI_AI_ENABLED를 활성화할 필요는 없다.
JEV는 별도의 JEV 설정과 Gemini 설정을 사용한다.

## MVP 이후의 확장 조건

- P1: P0 전체 사이클 검증 후 요약과 평문화를 각각 별도 품질 기준으로 구현·평가한다.
- P2 규정 판단: 사용자가 제공한 규정의 적용 대상·버전·필수 항목을 확정한 후 별도 계약으로 설계한다.
- P2 검색 답변: 약관 원본과 버전 관리, 검색·인용 검증이 준비된 후 시작한다.
- 추가 공급자: 11~16번에서 원래 계획대로 인터페이스·라우팅 기반을 만들되 최초 실연결 검증은 Gemini로 한다.
- 비동기 처리: 26번에서 작업 상태·재시도·중복 실행·취소 요구에 맞춰 구현한다.
- 대시보드: P0에서는 LangSmith의 원문 없는 운영 추적을 확인하고, 28번에서 통계·평가를 확장한다.

보험금 자동 지급·거절, 의료 진단·치료 추천은 후순위 기능이 아니라 권한 정책상 허용하지 않는 범위다.

## 완료 기준

- 후보 기능을 P0/P1/P2로 정렬하고 선행 조건을 정했다.
- 의료 JEV MVP에 포함할 처리·출력·검증 기준을 정했다.
- 규정 없는 작성 상태 점검과 규정 기반 제출 판단을 구분했다.
- 기존 코드 보존·향후 이관 범위와 28개 작업의 관계를 명시했다.
- 실연결 검증과 평가가 아직 필요한 부분을 드러냈다.
