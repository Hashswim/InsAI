# 작업 16 — 폴백·재시도·서킷 브레이커

상태: 공통 실행 계층, 안전한 오류 분류, 제한된 복구 정책과 동시성 검증 구현.
실제 .env·키·모델 등록·공급자 호출·규정 입력은 계속 보류한다.

## 기본 동작과 권한

기본 총 시도 횟수는 1회, 같은 모델 시도도 1회이며 폴백은 꺼져 있다.
추가 유료 호출이나 다른 모델 전송을 자동 활성화하지 않았다.
기본 서킷 브레이커는 같은 모델의 연속 일시 장애 5회 후 30초 동안 새 호출을 차단한다.
스텁에는 서킷을 적용하지 않고 재시도·폴백도 허용하지 않는다.

폴백을 명시적으로 켜려면 priority 정책과 총 시도 2회 이상이 필요하다.
후보는 서버의 JEV_MODEL_PRIORITY와 카탈로그에서 호환되는 동일 공급자 모델뿐이다.
Gemini→OpenAI, OpenAI→Gemini 또는 실모델→스텁 전환은 지원하지 않는다.
사용자 요청·문서 내용으로 정책을 변경할 수 없다.

## 오류별 복구

| 오류 | 재시도·폴백 | 서킷 장애 집계 |
|---|---|---|
| 500/502/503, HTTPX ConnectError | 명시적으로 켰을 때만 가능 | 집계 |
| OpenAI 429 중 rate_limit_exceeded/slow_down, 부족한 할당량 유형이 아닌 경우 | 위와 동일 | 집계 |
| 그 외 OpenAI 429, 결제·사용량 한도 | 하지 않음 | 집계 안 함 |
| Gemini 429 | 할당량과 일시 제한을 확실히 구분하지 못해 하지 않음 | 집계 안 함 |
| 타임아웃, HTTP 408/504 | 중복 처리·청구 가능성을 줄이기 위해 하지 않음 | 집계 |
| 인증·권한·잘못된 요청, 그 외 오류 | 하지 않음 | 집계 안 함 |
| 거절·불완전 응답·잘못된 구조/문서 근거 | 하지 않음 | 집계 안 함 |

SDK 내부 자동 재시도는 여전히 꺼져 있고 앱 계층에서만 시도 수를 센다.
분석에는 매번 동일한 request_id와 문서를 쓰지만 공급자의 멱등성이나 비용 중복 방지를 보장하지 않는다.
500 계열 등도 이미 원격 처리됐을 가능성이 있으므로 복구 옵션을 켜면 추가 청구가 생길 수 있다.
실행 중 요청 취소·클라이언트 재전송 중복 제거는 아직 구현하지 않았으며 후속 작업 범위다.

## 설정과 실행 한도

| 변수 | 기본값 | 제한·의미 |
|---|---|---|
| JEV_MAX_ATTEMPTS | 1 | 요청 전체 모델 시도 상한 1~5. 모델마다 초기화하지 않음 |
| JEV_RETRY_ATTEMPTS | 1 | 같은 모델의 총 시도 1~3. 전체 상한 이하 |
| JEV_FALLBACK_ENABLED | false | priority이며 전체 상한이 2 이상일 때만 true 가능 |
| JEV_ATTEMPT_TIMEOUT_SECONDS | 90 | 어댑터 한 번의 HTTP/SDK 타임아웃, 1~100초 |
| JEV_EXECUTION_BUDGET_SECONDS | 110 | 실행 계층의 시간 예산, 1~115초이며 한 번의 타임아웃 이상 |
| JEV_RETRY_BASE_DELAY_SECONDS | 0.25 | 지수 백오프 기준 0~2초, jitter 포함. 실제 한 번 대기 상한 2초 |
| JEV_CIRCUIT_ENABLED | true | 프로세스 내부 모델별 차단 사용 |
| JEV_CIRCUIT_FAILURE_THRESHOLD | 5 | 연속 일시 장애 임계 1~20회, 실제 시도 단위 |
| JEV_CIRCUIT_COOLDOWN_SECONDS | 30 | 차단 후 복구 확인까지 1~300초 |

재시도는 같은 모델에서 먼저 소진하고, 허용된 경우 다음 우선순위 모델로 이동한다.
모든 경로가 전체 시도 상한을 공유한다. 열려 있는 서킷은 호출 없이 건너뛰며 시도 수를 소비하지 않는다.
대체 모델 SDK는 필요할 때 한 번 생성해 캐시하고 요청별 결과·통계는 공유 가변 필드에 저장하지 않는다.
주 모델 SDK 초기화 자체의 오류는 호출 실행 전 구성 실패로 503 처리하며 자동 폴백하지 않는다.
대체 SDK 초기화 오류 역시 재시도하지 않는다.

형식 예: 검토한 두 모델을 등록한 뒤 아래처럼 명시적으로 복구를 켤 수 있다.
실제 .env를 변경한 예가 아니며 모델 ID는 실제 등록값으로 교체해야 한다.

```dotenv
JEV_ROUTING_POLICY=priority
JEV_MODEL_PRIORITY=["reviewed-first","reviewed-second"]
JEV_MAX_ATTEMPTS=3
JEV_RETRY_ATTEMPTS=2
JEV_FALLBACK_ENABLED=true
```

Retry-After가 유효하면 서버가 요구한 시간보다 일찍 다시 호출하지 않는다.
2초보다 긴 지연은 기다리거나 더 짧게 줄여 호출하지 않고 요청을 실패로 반환한다.
잘못된 헤더는 지수 백오프/jitter로 대체한다. 재시도뿐 아니라 같은 공급자 폴백에도 이 지연을 적용한다.
프로세스·요청 간 공급자 전체 rate limiter는 아직 없으며 17번에서 다룬다.

추가 시도 전 남은 예산이 설정된 한 번의 타임아웃과 대기시간을 수용하는지 검사한다.
예산 초과 뒤 도착한 결과도 성공으로 반환하지 않는다.
이 예산은 SDK 호출을 강제로 중단하는 hard deadline이 아니다. HTTPX의 단계별 타임아웃과
SDK의 호출 제한은 총 wall-clock 제한과 다르며 실행 중 호출을 강제 취소하지 못한다.
입력 검증·주 SDK 초기화·최종 LangSmith 기록 시간도 이 실행 예산 밖이다.
Spring 기본 120초 제한과 함께 운용할 때 실제 부하에서 시간 상한을 재검증해야 한다.

## 서킷의 상태와 동시성

CLOSED에서는 일시 장애와 타임아웃을 연속 집계하고 임계에서 OPEN으로 전환한다.
성공 또는 비집계 응답은 연속 가용성 장애 집계를 초기화한다. 이는 판정 품질 보증이 아니다.
OPEN은 새 모델 호출을 차단하고, cooldown 경과 후 HALF_OPEN에서 실제 요청 하나만 복구 탐색으로 허용한다.
동시에 들어온 다른 요청은 해당 모델을 호출하지 않는다. 정상 응답이면 CLOSED, 일시 장애면 다시 OPEN이다.
취소·초기화 실패 등으로 탐색을 수행하지 못하면 탐색 권한만 반납한다.

락과 세대 번호로 오래된 진행 중 요청의 성공이 새로 열린 서킷을 잘못 닫지 않도록 했다.
이미 실행 중인 호출은 취소하지 않는다. 상태는 공급자+모델별이며 요청 원문이나 사용자 식별자는 저장하지 않는다.
서킷은 프로세스 메모리 한정이다. 재시작하면 초기화되고 여러 worker/인스턴스끼리 공유하지 않는다.
관리용 강제 초기화 API·분산 상태 저장소는 추가하지 않았다.
readiness는 기존 설정·선택 가능성 검사이며 동적 서킷 상태나 실제 공급자 연결을 검사하지 않는다.

## 결과·추적·오류

API 경로는 ResilientJevService/ResilientExecutor를 사용한다.
각 시도마다 기존 워크플로로 구조·문서 근거를 검증하고 최종 성공 결과만 반환한다.
응답의 provider/model과 trace는 실제 성공한 모델을 사용하므로 Spring도 기존 계약으로 그 결과를 저장한다.
단일 시도용 JevService와 공급자 팩토리 자체에는 복구 루프가 없으며 직접 어댑터를 호출하면 서킷도 적용되지 않는다.

논리 요청당 안전한 LangSmith trace 하나를 시도하며 원문 inputs/outputs는 계속 빈 값이다.
기존 선택 메타데이터에 execution_attempts, execution_retries, execution_fallbacks,
execution_circuit_skips의 정수만 추가한다. 대체 모델 선택 이유는 SAME_PROVIDER_FALLBACK이다.
실패 시 원문 대신 고정 실패 코드와 마지막 실행 모델·통계만 사용한다.
실제 시도가 0회인 서킷 차단 실패에서는 최초 선택 모델과 0회 통계를 기록한다.
최종 토큰 수나 실패 시 0을 전체 비용으로 해석하면 안 된다.
17번부터 선택적 [추정 비용 예약](usage-limits.md)이 모든 시도를 같은 예산으로 관리한다.
LangSmith 미설정/실패는 기존 DISABLED/FAILED 동작을 유지한다.

모든 후보가 서킷으로 차단되면 기존 SERVICE_UNAVAILABLE 503,
실행 예산·타임아웃은 AI_TIMEOUT 504, 그 밖의 오류는 기존 502 계약을 유지한다.
Spring이 이미 503/504를 매핑하므로 Java·프론트엔드 계약은 변경하지 않았다.
규정은 비워 두며 제출 상태는 계속 ON_HOLD/NOT_REGISTERED다.

## 검증과 근거

가짜 시계·대기 함수·전송/모델을 사용해 실제 대기·유료 모델 호출 없이
단일 시도 기본값, 전체/모델별 상한, 지연·예산, 폴백, 영구 오류 미재시도,
서킷 차단/복구/단일 동시 탐색과 오래된 완료 무시를 검사한다.
HTTP 테스트는 두 공급자 각각의 동일 공급자 폴백 결과·trace·서킷 503을 확인한다.
동시 요청에서도 실제 모델 정보가 서로 섞이지 않는지 검사한다.

오류·Retry-After 구분은 OpenAI Docs 스킬로
[공식 오류 안내](https://developers.openai.com/api/docs/guides/error-codes)와
[공식 속도 제한 안내](https://developers.openai.com/api/docs/guides/rate-limits)를 확인해 반영했다.
타임아웃을 재호출하지 않는 것은 중복 청구 위험을 줄이기 위한 이 프로젝트의 보수적 정책이다.

2026-10-20: Python 3.11·3.14 각각 271개 테스트, Ruff·mypy(28개 소스)·포맷 검사 통과.
임시 로컬 포트의 실제 HTTP 운영·인증 스모크 테스트 통과.
Python 3.14의 기존 Google SDK DeprecationWarning 1건은 남아 있다.
Java·프론트엔드는 변경하지 않았으며 실제 외부 모델·키·운영 배포는 검증하지 않았다.
