# 프롬프트·체인 버전 관리

## 현재 릴리스

`back/ai-service/app/chains/release.py`의 변경 불가능한 `ACTIVE_RELEASE`가
서버 릴리스를 지정한다. 요청·헤더·환경변수·LangSmith 원격 프롬프트로 교체하지 않는다.

| 필드 | 현재 값 / 의미 |
|---|---|
| prompt_version | `jev-v2` — `chains/prompts/jev-v2.txt` |
| prompt_sha256 | 패키지에 포함된 UTF-8 파일 원본 바이트의 SHA-256, 줄바꿈 포함 |
| chain_version | `jev-chain-v3` — PDF 입력 매핑 → J의 단일 모델 초안 → 엄격한 원본 JSON/항목 검증 → 중복 판정 범위 검사 → 문서 ID·페이지 범위 검증 |

프롬프트 v2에서 J 판정 지침을 구체화했다. 규정은 비어 있고 제출 여부는 계속 `ON_HOLD`다.
J/E/V를 별도의 모델 호출 세 개로 구현했다는 뜻은 아니다. 재시도·라우팅은 별도 정책이며
기존 `router_version` 등 추적 메타데이터로 구분한다.
체인 버전은 코드 리뷰로 관리하는 의미적 버전이며 실행 코드의 자동 해시가 아니다.
v1은 최초 버전 관리 릴리스이며, v2에서 [공통 파싱 계층](structured-output.md)과
타입·원본 JSON 검증 기준을 강화했다. 프롬프트는 변경하지 않았다.
v3에서는 [J 체인](judgment-chain.md)을 연결하고 중복 범위 검증을 추가했으며,
프롬프트도 jev-v2로 올렸다. 과거 파일·저장 결과를 덮어쓰지 않는다.

## 실행·저장·추적

- 프롬프트 로더는 등록된 버전만 허용하고 경로를 직접 입력받지 않는다.
  비어 있거나 누락·변조된 파일은 고정된 오류로 거절하며 파일 경로·원문을 노출하지 않는다.
- Gemini와 OpenAI는 같은 검증된 원문을 사용한다. 모델 API 형식은 변경하지 않는다.
  최초 서비스 구성은 SDK 생성 전에 검증하며, readiness도 매번 파일 무결성을 확인한다.
  실패하면 readiness와 신규 서비스 구성은 503이다. liveness는 유지한다.
- 모든 성공 응답에는 세 필드가 필수다. 동일 공급자 fallback에서도 릴리스는 변하지 않는다.
  stub은 같은 워크플로 릴리스 정보를 기록하지만 실제 프롬프트를 모델에 보내지 않는다.
- LangSmith에는 세 식별자만 추가한다. 프롬프트·PDF·판정·근거 원문은 보내지 않으며
  inputs/outputs는 계속 빈 객체다. 성공·분석 실패 추적에 같은 릴리스 식별자를 사용한다.
- Spring Boot는 새 응답의 버전·해시 형식을 검사하고 결과 JSON에 그대로 저장한다.
  저장·재조회 테스트로 유지 여부를 확인한다. 별도 DB 컬럼·마이그레이션은 필요하지 않다.
  과거 저장 JSON에 없는 chain_version/prompt_sha256은 null이며 현재 버전으로 추정하지 않는다.
  새 HTTP 응답에는 세 필드가 필요하므로 Spring과 FastAPI를 함께 배포해야 한다.

## 변경·되돌리기 절차

1. 프롬프트를 바꾸면 기존 버전 파일을 덮어쓰지 않고 새 파일을 추가한다.
   현재 로더는 활성 릴리스 하나만 지원하므로 과거 파일이 있어도 임의 선택할 수 없다.
2. `shasum -a 256 app/chains/prompts/새버전.txt`로 파일 해시를 구한다.
   버전·해시·활성 릴리스를 코드 리뷰로 함께 변경한다. 런타임 자동 재계산으로 검증을 생략하지 않는다.
3. 워크플로 입력·단계·검증 의미를 변경하면 chain_version도 올린다.
   프롬프트만 변경하면 prompt_version/hash를 올린다. 공유 응답 예제·문서도 갱신한다.
4. Python 검사, 제공자 전송 원문 검사, fallback 응답/trace 일치 검사,
   Spring 공유 계약·저장/재조회 검사, 설치 패키지 smoke를 실행한다.
5. 검증된 빌드 아티팩트와 Git 커밋을 함께 보관하고 재배포·재시작한다.
   되돌릴 때는 이전 코드·프롬프트·의존성을 포함한 빌드 전체를 재배포한다.

실행 중 파일을 바꾸는 hot reload는 지원하지 않는다. 이미 구성된 서비스/제공자는 검증한
프롬프트를 메모리에 보관하므로 이후 파일 변조가 기존 실행을 취소하지는 않는다.
SHA-256은 우발적 변경을 탐지하는 장치이며 공격자가 코드와 파일을 함께 바꾸는 상황의
서명 검증을 대체하지 않는다. 같은 버전이라도 외부 모델의 비결정성·업데이트 때문에 결과가
완전히 재현된다고 보장하지 않는다. 모델 ID·빌드·의존성도 함께 관리해야 한다.

이번 작업은 로컬 릴리스 식별·무결성·저장 기반이다. 원격 프롬프트 레지스트리,
승인 UI, A/B 평가·자동 승격은 포함하지 않는다. J 구현은 별도 작업 20을 참고한다.
