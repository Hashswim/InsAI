# 작업 23 — JEV 오케스트레이터

## 실행 경계

`app/jev/orchestrator.py`의 무상태 `JevOrchestrator`가 시도 한 번을 조정한다.
기존 `run_workflow`는 이 오케스트레이터에 위임하므로 기본 서비스와 재시도 실행 경로가 같은 순서를 따른다.

고정 순서: PREPARE → J → E → V → VerifiedResult 반환.

- PREPARE: 요청 컨테이너를 복사해 호출자와 분리하고 내부 ProviderRequest로 매핑한다.
  PDF 문자열과 UUID는 그대로 사용한다. 기존 HTTP 입력·PDF 검증과 인가를 대체하지 않는다.
- J: 선택된 제공자에서 모델 초안을 한 번 요청하고 판정·중복 범위를 검사한다.
- E: 요청 PDF의 문서 ID·실제 페이지 범위와 중복 근거를 검사한다.
- V: 구조적 일관성을 최종 검사하고 사실성 미검증·사람 검토 필요 등의 서버 표시를 만든다.

단계를 건너뛰거나 순서를 바꾸지 못하며 각 단계의 반환 타입도 확인한다.
어느 단계가 실패하면 이후 단계는 호출하지 않고 성공 결과도 반환하지 않는다.
취소 등 BaseException은 삼키지 않으며 바깥 실행 계층이 자원 해제를 처리한다.
오케스트레이터 자체는 모델 선택·재시도·비용 예약·저장·trace 전송을 하지 않는다.

## 시도별 상태

`WorkflowProgress`는 **시도 하나에만** 사용하며 재사용을 거절한다.
오케스트레이터 인스턴스에는 요청 상태를 보관하지 않는다. 병렬 요청과 재시도마다 새 상태를 만든다.
진행 상태에는 완료 단계와 실패 단계만 있으며 PDF·근거·사용자/문서 ID·예외를 넣지 않는다.
스냅샷 `WorkflowReport`는 변경 불가능하며 허용된 단계의 순서만 수용한다.

LangSmith 수동 trace의 추가 허용 상수:

| 키 | 의미 |
|---|---|
| orchestrator_version | jev-orchestrator-v1 |
| last_workflow_completed_stages | 마지막 실제 시도의 완료 단계, 예: PREPARE,J,E |
| last_workflow_failed_stage | 마지막 실제 시도에서 실패한 단계 또는 NONE |
| last_workflow_status | COMPLETED / FAILED / INCOMPLETE |

PREPARE도 완료 단계에 포함한다. 단계 상태는 API 응답이나 업무 DB의 새 컬럼이 아니라 운영 추적 정보다.
오케스트레이터는 원래 예외를 바깥 실행 계층에 넘기며, 기존 계층이 고정된 안전 오류로 정규화한다.
진행 상태·보고서에는 원본 예외를 저장하지 않는다. 자동 단계별 LangChain/LangSmith trace를 추가하지 않는다.

## 재시도·제한과의 관계

기존 ResilientExecutor가 모델·시도 수·지연·서킷·실행 시간·비용을 관리한다.
J의 일시적 공급자 오류만 기존 정책에 따라 새 시도를 시작할 수 있다.
E/V는 로컬 검사이므로 일시적 공급자 오류 형태가 올라와도 InvalidProviderResponse로 바꿔
이미 비용이 발생한 J를 재실행하지 않는다. 보통의 파싱·근거·검증 오류도 계속 즉시 종료한다.

재시도는 PREPARE부터 새로 시작하고, 이전 시도의 초안·일부 근거·검증 표시를 이어 붙이지 않는다.
execution_attempts/retries/fallbacks는 요청 전체의 기존 집계값이다.
last_workflow_*는 **마지막 실제 워크플로 시도만** 나타내며 모든 과거 시도를 나열하지 않는다.
첫 시도가 실패해도 fallback이 성공하면 마지막 보고서는 COMPLETED다.

모델을 호출하기 전에 서킷·한도·설정으로 막힌 요청은 워크플로 보고서가 없다.
이전 시도 뒤 한도 등으로 중단됐다면 마지막 실제 시도의 보고서를 유지한다.
워크플로가 완료돼도 이후 비용 상한/시간 제한 때문에 요청 전체가 실패할 수 있다.
따라서 last_workflow_status=COMPLETED는 최종 분석 성공이나 제출 승인을 뜻하지 않으며
trace의 성공/실패·기존 실행 통계와 함께 해석해야 한다.

## 버전·검증·제한

작업 23 당시 체인은 jev-chain-v6이며, 현재 작업 24의 [입력 방어](input-defense.md)는 jev-chain-v7이다.
프롬프트는 변경 없는 jev-v2다. API 응답 스키마·DB 컬럼·환경변수는 추가하지 않았다.
규정은 비어 있고 제출 여부는 ON_HOLD다. 구조적 V의 사실 검증·신뢰도 보정 한계도 그대로다.

고정 순서, 잘못된 반환 타입, 단계 실패 후 중단, 취소 전파, 상태 재사용 금지,
요청 컨테이너 분리, 병렬 성공/실패의 상태 격리, 재시도·fallback 후 마지막 상태,
서킷 사전 차단 시 보고서 없음, E/V 오류로 유료 J 호출을 재실행하지 않음을 자동 테스트한다.
API 오류·trace에 원문이 없고 V 실패에서 검증 통과 표시를 남기지 않는지도 검사한다.

이는 프로세스 내 동기 실행 조정자다. 영속 작업 상태·작업 큐·재시작 복구·중복 실행 방지는
작업 26 등 후속 범위이며 이번 단계에 구현하지 않았다. 실제 모델 호출·의료 문서 정확도 평가도 하지 않았다.
