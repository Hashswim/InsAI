# Phase 1 — 도메인 분석

## 한 줄 정의

**AI 중립 청구 협업 공간.** 보험 청구인(계약자)과 손해사정사가 같은 화면에서 소통하되, 그 사이를 AI가 중개한다.

## 문제

청구 서류 접수는 사정사가 필요한 서류를 요청하고 → 청구인이 서류를 준비·제출하고 → 사정사가 검토하는 왕복 과정이다.
현재는 이 과정이 비정형(전화·이메일·방문)이고, 청구인은 무엇을 어떻게 채워야 할지 모른다.

## 해결

1. **정형 양식 템플릿** — 사정사가 요청하는 서류마다 "미리 저장된 칸" 구조(`FormTemplate`)가 있다.
2. **AI 구조화** — 청구인의 입력을 템플릿 칸에 맞춰 채우고, 누락 필드를 계산한다 (`AiStructurePort`, 현재 규칙 기반 스텁).
3. **AI 요약·하이라이트** (예정) — 사정사에게 제출물 요약·핵심·누락 여부를 정리해 준다.
4. **AI 평문 번역** (예정) — 사정사의 판단을 약관 근거와 함께 청구인이 이해할 평문으로 옮긴다.

## 핵심 개념

| 개념 | 설명 | 모듈 |
|---|---|---|
| Account | 청구인(CLAIMANT) / 손해사정사(ADJUSTER) / 운영자(ADMIN) | auth |
| Case (청구 협업 공간) | 청구인 1 + 사정사 1 의 방. 상태 머신으로 진행 | collab |
| DocumentRequest | 사정사가 "이 서류 주세요"라고 만드는 요청. 템플릿을 지정 | collab |
| FormTemplate / FormField | 서류의 칸 구조. code + version | form |
| FormSubmission | 청구인이 채운 값 + AI 구조화 결과 + 누락/검증 결과 | form |
| Decision | 사정사의 판단(rawText) → AI 평문(plainText) | collab |
| TimelineEvent | 케이스 활동 로그 (감사 + UI 피드) | collab |
| StoredFile | 첨부 파일 메타 + OCR 텍스트 | document (예정) |

## 청구 유형 (생명보험, 1차 범위)

`form.catalog` 에 생명보험 청구 서류 카탈로그를 구현했다. 상세는
[features/life-insurance-claim-documents.md](features/life-insurance-claim-documents.md).

| 유형 | 코드 | 대표 추가 서류 |
|---|---|---|
| 사망보험금 | DEATH | 사망진단서, 가족관계·기본증명서, (재해 시) 사고사실확인원 |
| 후유장해보험금 | DISABILITY | 후유장해진단서, 검사결과지 |
| 진단보험금 | DIAGNOSIS | 진단서, (암) 조직검사결과지 |
| 입원·수술급여금 | HOSPITALIZATION_SURGERY | 입퇴원확인서, 수술확인서, 진료비영수증·세부내역서 |

## 액터와 목표

| 액터 | 목표 |
|---|---|
| 청구인 (CLAIMANT) | 케이스 개설 → 요청받은 서류를 쉽게 채워 제출 → 결과를 이해 |
| 손해사정사 (ADJUSTER) | 청구 유형에 맞는 서류 요청 → 제출물 검토(요약·누락) → 결과 등록 |
| AI (중개) | 입력 구조화, 누락 탐지, (예정) 요약·평문 번역·약관 기반 1차 응답 |
| 운영자 (ADMIN) | 사정사 계정 승인, 템플릿 관리 |

## 비목표 (현재 범위 밖)

- 보험료 산출·언더라이팅·계약 관리 (보험사 코어 시스템 영역)
- 실제 보험금 지급/정산
- 손해보험·제3보험 (생명보험만 우선)
- 실시간 채팅 (메시지 스레드는 폴링 수준)
